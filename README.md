# Jackintosh ROMs

Boot ROMs that turn an Atari ST, STE, Mega ST or Mega STE into a
Macintosh Plus at power-on. There is no TOS, no GEM and no emulator
program. The Atari's own 68000 runs the genuine Mac Plus v3 ROM natively,
and a layer of our code, the **glue**, replaces the Macintosh hardware
the Atari does not have.

**To use it, go to <https://jackintosh.sidecartridge.com/>.** The site's
image builder merges your own Mac Plus ROM with this repository's glue in
your browser and gives you the image. This README is for developers.

## The pieces

- **This repository**: the glue (Atari boot, RAM sizing, interrupts and
  timing, Shifter video, IKBD keyboard and mouse, a Mac disk driver, the
  cartridge protocol, the disk chooser), the **patch table** applied to
  the Mac Plus ROM, the merge tool, and the website.
- **The SidecarTridge TOS Emulator** sits in the TOS ROM sockets and
  serves our image as the system ROM: 192 KB at `$FC0000` on the ST, STF,
  STFM and Mega ST; 256 KB at `$E00000` on the STE and Mega STE.
- **The SidecarTridge Multi-device** in the cartridge port runs the
  [md-jackintosh](https://github.com/sidecartridge/md-jackintosh)
  microfirmware. It serves Macintosh floppy and hard-disk images from its
  microSD card, the time over NTP and the Mac's parameter RAM, over the
  cartridge bus. The two repositories share a protocol (`src/glue/cart.h`
  here, `rp/src/include/macdisk.h` there) and change it together.

## No Apple bytes

The Mac Plus ROM is Apple's copyrighted code. **No Apple-derived byte is
ever committed or published**: no ROM dump, no assembled ROM, no merged
boot image, no disk image with Apple system software, no hex dump of ROM
regions. The repository holds only our glue, our patch table and the
tools; `.gitignore` keeps `*.rom`, `*.img`, `*.dsk`, `build/` and the like
out, so leave it as it is.

Each developer brings a Mac Plus v3 ROM: 131072 bytes, stored and computed
checksum `$4D1F8172`, version word `$0075` at offset 8. Either a dump of
your own, or assembled from
[jonathanschilling/mac_rom](https://github.com/jonathanschilling/mac_rom)
(the `external/mac_rom` submodule, pinned at `1d1014e`), which builds it
byte-identical (SHA-256 `dd908e2b…7895e7`). mac_rom's commented source is
also the reference for every patch.

## How it works

```
 $FC0000 / $E00000          Atari reset header, then the glue
 + 64 KB  / + 128 KB        the Mac Plus v3 ROM (ROMBase), every byte at its offset
```

- **The ROM keeps every offset.** System 6's patches depend on exact ROM
  offsets, so each patch replaces bytes with the same number of bytes,
  usually a `JMP`/`JSR` into the glue. `src/patches/plus_v3.ini` lists
  each one: offset, length, the SHA-256 of the original bytes (never the
  bytes), the replacement, the mac_rom file and line, and the reason. The
  merge refuses a ROM that differs at any patch site.
- **System 6.0.7 and 6.0.8 are relocated as they load.** Their `PTCH`
  resource holds absolute `$40xxxx` ROM addresses; the glue wraps
  `jCheckLoad` and moves them for known resources (`sysreloc.c`, its table
  generated by `tools/sysreloc.py`).
- **Boot**: `startup.s` sizes RAM as TOS does and copies `.data`;
  `main.c` talks to the Multi-device, shows the disk chooser (`menu.c`),
  then `mac.c` sets the Mac's low memory and jumps into the ROM's reset.
  The ROM calls back into the glue through the enabled patches.
- **The Mac hardware**: the VIA, SCC and IWM live in RAM shadows
  (`shadows.s`). MFP Timer C gives the 60 Hz tick; the HBL and VBL
  autovectors are redirected; the IKBD becomes the Mac's keyboard and
  mouse (`ikbd.c`); the RTC and PRAM are emulated (`mac.c`); `disk.c` is
  the Mac disk driver over a backend: the cartridge (`cartdisk.c`), a RAM
  disk in test builds (`ramdisk.c`), or none. `buserr.c` gives Plus
  behaviour to accesses the ST would fault on: writes to `$0`–`$7`, the
  Plus's ROM and device addresses.
- **Video**: 640x400 mono (`ScreenRow` 80), or the Plus's 512x342 at the
  top left of the frame in a black border.
- **Sound** (STE and Mega STE): the Plus's sound buffer resampled onto
  the DMA sound each tick (`sound.c`, `sound.s`).

## Building

You need Docker (the toolchain is a pinned image,
`logronoide/atarist-toolkit-docker-x86_64:1.4.0`), Python 3, and for the
website Node.js 22 or later.

```bash
git clone --recurse-submodules git@github.com:sidecartridge/md-jackintosh-roms.git
cd md-jackintosh-roms
cp tools/dev/dev.cfg.example tools/dev/dev.cfg   # local paths; git-ignored

tools/macrom.py build              # assemble mac_rom's Plus v3 into build/macrom/ and check it
                                   # (or set [macrom] file in dev.cfg to your own dump)
tools/dev/build.sh st release      # the glue, out of tree into build/st-release/ (GLUE.BIN, GLUE.MAP)
tools/dev/build.sh ste debug-test  # machines: st | ste; types: release | debug | test | debug-test
tools/jackrom.py merge --machine st --glue build/st-release/GLUE.BIN -o build/JACKINTOSH-ST-v1.0.0.img
tools/jackrom.py patches           # check every patch entry against the ROM
make format-check                  # clang-format; also format, tidy, check
```

Build types:

- **release**: what goes on hardware.
- **debug**: adds the `@@` trace over NatFeats and traces faults (registers,
  code, stack) instead of letting the Mac bomb. **Never on hardware**: the
  NatFeats call traps on a real ST.
- **test**: adds the RAM-disk backend, a second floppy, and mailboxes the
  harness writes to (input, disk swaps, a fake Multi-device).
- **debug-test**: both; what the harness uses.

The code is freestanding: no TOS call, no libc, no libgcc (a 32-bit
division GCC cannot fold fails to link, so build every change in debug
too). Code and constants run from ROM; `.data` is copied to RAM and `.bss`
cleared. `src/glue/mem.h` holds the memory layout, shared by C, assembly
and the linker script. A new `.c` file goes into `SRCS_C` in
`src/glue/Makefile`. Functions are camelBack, and every source file
starts with the `File / Author / Date / Copyright / Description` block.

## Testing in Hatari

Every change runs in [Hatari](https://hatari.tuxfamily.org/) (2.6) before
it reaches hardware. The harness boots the merged image as the system ROM,
reads the `@@` trace, drives keys and the mouse, and takes screenshots.
Hatari has no SidecarTridge, so test builds read disks from a RAM disk the
harness loads at the top of ST RAM, and `--fake-cart` answers as
md-jackintosh would.

Name your disk images (System 6.0.8, programs) in `tools/dev/dev.cfg`'s
`[disks]`; they stay outside the repository. Run Hatari with a clean
`HOME` if your own `hatari.cfg` changes its defaults.

```bash
python3 tools/dev/hatari_harness.py --image ste --memsize 4096          # boot to the "?" disk
python3 tools/dev/hatari_harness.py --image st --memsize 4096 --type debug-test --disk @system608 --input
python3 tools/dev/hatari_harness.py --image st --memsize 4096 --type debug-test --disk @system608 --interactive
python3 tools/dev/hatari_harness.py --image st --memsize 4096 --type debug-test \
    --disk @system608 --disk2 @word40a --launch 85,56 --then keys:Hello --then shot:typed
tools/dev/all_harness.sh            # every build and every session (~13 min); also megaste, megaste16
```

Each run leaves `build/harness/<stamp>-<label>/` with `trace.txt`,
Hatari's log and `shots/`.

- **Scripting a session**: `--then` takes `click:V,H`, `cmd:KEY`,
  `keys:TEXT`, `press:`/`release:` for menus, `wait:S`, `shot:NAME`, and
  checks: `expect:REGEX` on the trace, `dark:` on a screenshot.
- **Debugging aids**: `--watch ADDR` (registers whenever the CPU reaches
  ADDR), `--watch-mem ADDR` (whenever a long changes), `--dump ADDR:LEN`,
  `--then regs`, `--then mem:ADDR,LEN`.
- **Disks**: `--fixed` makes a hard disk, `--swap` queues floppies, and
  `tools/dev/mkhd.py` builds a bootable hard-disk image from items of
  other images (it needs `machfs`:
  `python3 -m venv build/venv && build/venv/bin/pip install machfs==1.3`).

A Hatari pass says nothing about the cartridge bus, the TOS Emulator, real
Shifter timing or power-on behaviour; those are checked on the bench with
a release build.

## The website

`site/` is <https://jackintosh.sidecartridge.com/>: the image builder and
an illustrated guide to how the glue works. `cd site && node build.mjs`
writes `site/index.html` (commit it with any change to `site/src/` or
`SOFTWARE.md`; CI checks they match), and `node --test tests/*.test.mjs`
tests the merge in JavaScript. On each push to `main`, the Pages workflow
builds the release glue of both machines, exports the builder's data
(`tools/jackrom.py export`: glue, patches and hashes, no Apple byte) and
publishes the site.
